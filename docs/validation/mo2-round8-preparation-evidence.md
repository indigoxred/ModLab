# Round 8 protected preparation

The maintained gate requires caller-configured, disjoint disposable and authority run roots, derived from the same fresh run ID. A historical disposable-only attempt is never relabeled, copied into new authority, adopted, or modified. Preparation creates a fresh native verified vault and keeps its root/ancestor guards through both delegated bootstrap/configuration flows and protected publication.

`preparation.json`, `preparation-effect.json`, `preparation-originals.json`, and preparation `failure.json` are in the authority run vault. Installation, installation failure, restart, selection and envelope records also use that vault. The shared ContainmentStore adapter receives collection parents; GateConfig.authority_root is the actual run vault. No Task6 intent is created merely to capture a file.

## Original inputs

Preparation captures nine files through the shared bounded exact capture API: the maintained harness, windows_exact_fs helper, release descriptor, and each layout's artifact metadata, ModOrganizer.ini and nxmhandler.ini. Each destination has immutable `.capture.json` provenance binding original source path, volume/file identity, byte count, SHA-256 and Preparation stage. Every capture is limited to 2 MiB. Protected gate JSON reads are limited to 16 MiB, except the exact run-root `preparation.json`, which has a separate 64 MiB bound. The real curated two-layout preparation is 30,034,466 bytes because it retains both full bootstrap records and the complete path admission. Other records, logs and screenshots retain their existing limits; a same-named nested file does not receive this allowance. Native size checks reject oversized evidence before content reads. The record schema and immutable failed-attempt policy are unchanged. Final paths, provenance and publisher candidate names are admitted before mutation.

The independently protected preparation-originals record retains original source/archive/extractor/game observations plus each layout's retained-payload observation, relocation, configuration, runtime identities and writable baseline. Archives and runtime/game executables are represented by original native file/hash observations, not copied in full. Bootstrap plan/receipt/journal records remain structurally cross-validated. Journal stage and activated inventories describe the complete configured manager and must match each other in hash and count. The receipt's package inventory describes the extracted app, so its hash is a different scope; the configured manager cannot contain fewer files than that package. The existing plan, job and receipt identity bindings remain required. The existing release parser parses the protected release bytes. Original captured configuration bytes still must match the exact rendered contained configuration and noregister marker.

Historical `_load_preparation` reads only protected records/captures. It checks fixed destination paths before reading, exact provenance, source identity bindings, hashes and sizes. It never rereads a current Low archive/config/runtime or probes current Git/integrity/directory state. The tests record actual capture returns and guarded read paths in scratch inventories; fixture archive/game/extractor observations are explicitly synthetic, while vault policy, native pins, captured bytes and provenance execution are real.

## Current-use admission

`_fresh_preparation_preflight` first reconstructs protected history and then verifies current Git/harness/helper, curated release, original archive, extractor, game root/executable, retained archive metadata/payload, relocation/app/parent identities, configured directories, INI/marker, Low labels, runtime identities/version and writable root identities. Historical success alone does not authorize an action.

ProductionLiveBackend.source_check, direct begin and install, current load_state, finalization, and restart before cleanup/mutation reach that preflight. Public phase/install routes and their CLI dispatches retain source_check; CLI restart/finalize reach the corresponding checked actions. Process absence, plugin/runtime snapshots, writable transition checks and subsequent native launch checks are retained. Cleanup uses the same original process/job owner and shared causal reader described below.

Failure handling preserves preparation effects and explicit native ownership. Both capture/provenance writes enter the ledger before the shared capture call because publication may succeed before a later readback/close error. A secondary failure-publication ownership error is unioned with the primary capture ownership instead of discarded. Successful preparation and failure records remain immutable; restart publishes a separate record under a fresh paired run.

## Phase and final evidence

The maintained ten-phase flow stores each phase under `authority/<run>/<layout>/jobs/<phase>`. That directory contains begin.json, process.json, operator-evidence.json, runtime-delta.json, observation.json, effect.json, guarded.json when applicable, phase-final.json, immutable failure.json and separate cleanup.json. Its watch directory contains the shared request, claim, launch, ready, events, admission, quiescence, stop, terminal, worker-exit and outcome originals. The separate `disposable/<run>/<layout>/jobs/<phase>` remains Low child work; app, candidate and environment roots remain disposable.

The suspended launcher uses retain_owner=True and admits the original ProcessLaunch.owner to the shared watcher before resume. Native HWND correlation borrows that owner's process handle. Completion observes the original root exit and zero active job processes, calls complete_watch_launch, then the shared normal stop closes ownership and publishes original-controller worker-exit evidence. The gate calls watch_receipt_from_files to reconstruct raw evidence and compares summary IDs; it never supplies its own successful exit proof. Missing causal originals, recovery-only stop, poisoned ownership and outcome-only claims cannot complete a phase.

Validated PNG or JPEG bytes received directly through the operator exchange are published unchanged as protected window.png or window.jpg originals, bounded to 16 MiB. The corresponding protected .capture.json binds source kind, screenshot ID, stage, exact byte count and SHA-256. No Low screenshot staging file is created. Source MO2 logs are captured through ContainmentStore.capture_evidence_file into observed-000.log through observed-127.log, with native source identity and matching .capture.json provenance, bounded to 16 MiB each. Reconstruction reads protected bytes and provenance only. Screenshot and log captures enter attempted-write receipts before fallible publication; the live watcher journal is never snapshotted for effect bookkeeping.

Historical phase, cleanup, restart and envelope readers reconstruct protected originals. Current load_state/finalization and new action entry points retain fresh preparation, process absence, plugin/runtime and writable-state checks. After reconstructing completed phases, load_state also compares current protected plugin/runtime/profile snapshots and native watch-root identities with the last protected phase; begin, install and finalization reach this current-action check. Historical phase reconstruction does not reread those Low inputs. Incomplete attempts with missing original tree ownership refuse cleanup and restart. A separately raw-validated already-Completed chain is the known-closed historical case; immutable attempt failure is never removed or upgraded. Selection and envelope require schema-3 matrices with distinct disposable root and authorityRoot bindings.

## Verification boundary

The maintained offline suite retains explicit synthetic archive/game/process/window/watch seams. Synthetic parser fixtures are not native controller-exit or Computer Use proof. Native vault, exact publication/read/capture and failure-owner tests execute real Windows operations; focused process/job/watcher integrations separately verify the shared native lifecycle. Standalone `tests/test_mo2_round8_gate.py --scratch <fresh-dir> --log <fresh-log>` preserves the no-live-actions receipt. Actual capture/read inventories are exported from test interception into supplied scratch. Full repository verification and independent standalone execution remain controller-owned after scoped review; this document does not claim live MO2/game/UI validation.


Gate app/plugin/runtime/writable inventories and log discovery use the existing exact snapshot with a fixed limit of 16,384 descendant files/directories per snapshot (the root is held separately). The next entry causes explicit refusal, never truncation. Discovery and membership rechecks enumerate lazily within the budget before content reads; all accepted descendants stay pinned through final membership/identity checks. Every snapshot rejects more than 128 `.log` files and checks the native 16 MiB per-log size before reading its content. Final capture still enforces 128 logs across the app and manager collections together. Ordinary executable/artifact inventory hashing streams in 64 KiB native chunks, with no blanket 16 MiB binary cap. Generic snapshot callers retain their default limits. A legitimate tree above the entry budget requires a reviewed limit/scope adjustment; it is not silently accepted.

Public installation errors carry accumulated successful installation effects and the real protected failure-publication receipt, including publication followed by an ordinary exception. Existing primary causes and retryable native ownership remain attached; simultaneous native close failures retain their union.

The protected preparation originals retain the inspected archive listing once, in its original order, including file/directory kinds and its canonical listing hash. Its count/hash must match the captured release and both bootstrap plans. Existing `bootstrap_paths` / `admit_paths` reconstruct each preview budget (zero-job Create plus Adopt) and actual journal budget (real-job Create) separately, using the retained payload path; each recorded budget must equal its own reconstruction. The shared archive-path validator checks kinds, safe relative paths, duplicates and order-sensitive hashes. Missing listing originals remain a refusal; historical failed attempts are unchanged.

INI reconstruction uses the captured release descriptor's product version (`2.5.2`), as the production bootstrap writer does. Executable identity separately uses its file version (`2.5.2.0`). These values are not interchangeable; the complete captured INI bytes must still match the reconstruction.

The initial native window observation allows up to 30 seconds for MO2 to create a visible HWND, rechecking original process identity and liveness on each attempt. Waiting uses the retained process handle so termination interrupts startup. The observation after Computer Use remains immediate, and stable-window correlation remains required.

Failed-phase cleanup proves process and watcher closure even when the original event journal is nonempty. The raw causal reader, complete outcome hash, event bytes/count/identity, and exact process/root bindings remain required. Events remain preserved and the attempt remains failed and ineligible; successful phase unchanged checks are unaffected.

JPEG acceptance uses Pillow 12.3.0 from `tools/requirements-round8.txt` only when decoding JPEG evidence; the main ModLab commands do not import it. The original bytes are never converted or re-encoded. MIME, signature and extension must agree; complete decoding is bounded by the existing 256 MiB decoded-image limit. Existing PNG validation remains intact. Both exact filenames and provenance destinations are admitted before launch and reconstructed from protected records.


## Approved disposable active profile boundary

Fresh preparations under harness policy 2, runtime policy 3 and fixture version 3 implement the user-approved profile separation. MO2 selects `manager/test-profiles/ModLab - Lab` through its native `[Settings] profiles_directory=%BASE_DIR%/test-profiles` override. Preparation copies the Lab seed to distinct file/directory objects and binds equality of relative names, kinds, lengths and hashes to the protected Manager baseline. Originals remain in `manager/profiles` and retain the existing eight-root watch and zero-event proof.

The layout, bootstrap and manager ancestors remain Medium integrity, as do the original profiles, source mods, downloads and overwrite. Low labels are applied only to the app, environment, manager logs/webcache/cache and test-profiles trees. Exact receipts bind all six targets per layout, and current admission checks the Low roots and Medium original entries/ancestors.

Runtime deltas permit saved files only below the exact disposable Lab directory, plus the exact app ModOrganizer.ini and existing writable runtime roots. The disposable Lab directory itself cannot be replaced. The durable chain compares full before/after inventories and rejects unexplained changes between phases. This records persistent disposable state; it does not claim a complete event history of transient writes in disposable storage.

Every completed phase retains the original saved ModOrganizer.ini, bounded to 2 MiB, with Configuration-stage native capture provenance. Reconstruction matches its bytes, size and original file identity to the App delta, then compares required settings against the protected prepared INI. Game/base/profile selection and local-save policy cannot change; optional directory overrides must resolve to the declared exact destinations. Window preferences may be saved. Historical verification reads only protected captures. Current action admission checks the live configuration semantics, then the existing durable chain requires equality with the latest recorded state.

Earlier failed attempts remain untouched and ineligible. These policies supersede the active-profile zero-write requirement for new Round 8 attempts only; normal ModLab storage, scanner behavior and the shared watcher protocol are unchanged. The approved implementation plan is `docs/superpowers/plans/2026-09-05-round8-disposable-profile.md`.


## Runtime observations and support verdict

The original capability task requires recording cache creation. Runtime policy 3 admits bounded App/plugins cache observations only in a direct `__pycache__` directory with corresponding `.py` source files in the same inventory, using CPython 3.12 cache names (including optimization suffixes). Unknown caches and bytecode elsewhere remain a refusal. No entries, hashes or identities are filtered out. Declared candidate installation still cannot include bytecode. These records describe observed bytes and do not assert that a cache is safe executable content.

The capability selector is unchanged: full Control.after is frozen, and every later phase's full plugin tree must equal that baseline plus the declared candidate. Candidate cache creation or any later plugin drift still produces `NotSupported`. The gate records that measurable outcome rather than confusing it with malformed evidence. No bytecode suppression, permission trick, deletion or new baseline is used to force a supported result.

App logs/webcache/cache directories and their contents may be created, updated and rotated under the same bounded transition policy already used for Manager runtime output. The exact nxmhandler.log is also recorded. The fixed crashDumps directory is prepared empty; unexpected crash contents remain outside the accepted runtime policy. Ordinary package/runtime source files remain immutable.

The child environment binds PROGRAMDATA and ALLUSERSPROFILE to the disposable Environment/PROGRAMDATA directory and SystemDrive to the validated Windows drive. This addresses the first real run's literal `%SystemDrive%` cache tree and missing shared-data path. Ambient environment variables remain excluded, and Python bytecode flags remain prohibited. A real rerun is required to verify the Windows/NVIDIA behavior under these corrected bindings.

The live operator exchange first requests `wait-for-main-window`. After Computer Use observes the ready main window, the operator replies with exactly `{"ready":true}`. This only synchronizes startup: the controller then collects native-before, requests a fresh screenshot, and collects native-after. The original PID/creation identity, HWND, class and title must still match across that bracket. A startup screenshot cannot be reused as authoritative evidence. Readiness failure follows the existing retained-owner failure/cleanup path.
